## §4. 설계 — 추론을 «전부» 없앤다

### 4-1. 핵심 착상

계수를 **KIS 두 피드의 비**로 정확히 구한다.

```
adj_factor(date) = vol_adj(date) / vol_raw(date)
```

🔴 **정정(2026-08-20, 구현 계획 작성 중 발견)** — 초안은 `vol_raw / vol_adj` 였는데 **방향이 뒤집혔다.**
저장 규약은 `adj_close = raw_close / adj_factor` 이고 읽기 계층은 `volume × adj_factor` 를 하므로

```
adj_factor = raw_close / adj_close = vol_adj / vol_raw
```

실측 `054940` 2026-05-29: 가격 760/3,800 = **0.2** · 거래량 71,465/357,326 = **0.2** — 둘이 같고,
DB 에 실제 저장된 값도 **0.2** 다. 검산: 357,326 × 0.2 = 71,465 ✅.
***초안대로 5.0 을 썼으면 25배 틀렸다*** — §5-1 이 발견한 `025440`(24.3배 · 방향 뒤집힘)과
**같은 형태를 우리가 새로 만드는 꾴**이었다. 화이트리스트도, 정수 스냅도, 큐 `ratio` 도 필요 없다.
⇒ **255건 전부 계산된다** (21.6% 한계 소멸).

### 4-2. 종목별 처리

전체 이력을 **두 번** 받아 컬럼별로 출처를 가른다. **기존 규약을 한 글자도 안 바꾼다.**

| 컬럼 | 출처 | 근거 |
|---|---|---|
| `open`·`high`·`low`·`close` | `adj_prc="0"` | 규약 = 조정 연속 시세(§2-3) |
| `volume` | `adj_prc="1"` | 규약 = 원본 |
| `adj_factor` | **`vol_adj / vol_raw`** | 정확값 (방향 주의 — §4-1 정정) |
| `trading_value`·`market_cap` | 손대지 않는다 | 범위 밖 |

⇒ **읽기 계층 0줄 · 소비자 전원 무영향 · 두 번째 규약 없음.**

### 4-3. 계수 산출 시 주의

- `vol_adj == 0`(거래정지 패딩·휴장) 인 날은 **계수를 못 구한다** → 그 날은 건너뛰고,
  **같은 «구간»(이벤트 사이) 안에서 가장 가까운 유효 계수**를 쓴다 — 계수는 구간별 상수라 안전하다. **구간 경계를 넘어 빌리지 않는다.**
- 종목 전체에서 계수가 **하나도** 안 구해지면 그 종목은 **건드리지 않는다**(fail-closed).
- 구해진 계수들이 한 구간 안에서 **서로 다르면** 그 종목은 **건드리지 않고 ERROR 로 보고**한다.
  🔑 *「없다」와 「고장」을 같은 값으로 보고하지 않는다* — 이 저장소가 반복해서 데인 자리다.

## §6. 안전장치

### 6-1. 백업 (필수)

`daily_prices_preadj_backup` 테이블에 **손대는 행 전부**를 원본째 저장한다
(`stock_code, date, open, high, low, close, volume, adj_factor, backed_up_at, batch_id`).
롤백 = 백업에서 되돌리기. **백업 없이는 한 행도 안 고친다.**

### 6-2. 멱등

이미 조정된 행을 또 조정하면 망가진다. 판별은 **가격 비교로** 한다 —
`adj_prc="0"` 값과 DB 값이 이미 같으면(상대오차 1% 이내) **건너뛴다**.
🔑 *«가격이 이미 조정됐나» 를 `adj_factor` 로 판별하지 않는다* — 6번 결함 때문에 그 값을 못 믿는다.

🔴 **정정(구현 계획 작성 중)** — 단 「이 행을 고쳐야 하나」 판정에는 `adj_factor` 를
**반드시 포함**해야 한다. 가격은 멀줦한데 계수만 틀린 종목이 실측 **9건**이고(§5-1),
가격만 비교하면 그 9건을 «고칠 필요 없음» 으로 조용히 넘긴다.
⇒ **조정 여부 판별 = 가격** / **수정 필요 판별 = 가격 + 계수**. 둘을 가른다.

### 6-3. 단계적 적용

1. **1종목**(`054940`) → 전후 비교 인쇄 → 사람이 확인
2. **10종목** → 불가능봉 개수 감소 확인
3. **전체 243건**

각 단계에서 **불가능봉 개수**를 재고, **줄지 않으면 중단**한다.

### 6-4. 검증 (각 단계)

- 처리 종목의 `|일간수익률| > 30%` 봉 수가 **0 이 되는가**
- 처리 «안 한» 종목의 그 수가 **안 변하는가**(부작용 없음 대칭 확인)
- 전체 `daily_prices` 행 수 **불변**(UPSERT 만, DELETE 없음)
- 🔴 **`volume` 은 불변이어야 한다** — 기존도 원본, 새로 넣는 것도 `adj_prc="1"` 원본이다.
  바뀜다면 어떤 전제가 틀렸다는 뜻이므로 **즉시 중단**한다.
- `adj_factor` 는 **바뀌는 게 정상이다**(그게 이 작업의 목적 중 하나) —
  §4-1 계산값과 일치하는지만 확인한다.
  ⚠️ *초안은 「`volume × adj_factor` 불변」을 검산식으로 썼는데 그건 **설계대로면 반드시 실패한다*** —
  게이트가 자기가 막아야 할 것을 못 재는 계열의 오류라 사양 검토에서 정정했다.

### 7-1. 🆕 세 번째 경로 — 우리가 고친 `adj_factor` 는 **그날 저녁 되돌아간다**

초안은 이 경로를 **아예 빠뜨렸다.** 매 EOD 마다 `daily_collector.py:102` 가
`update_adj_factors(conn)` 를 부르고, 그 경로(`collectors/daily_adj.py`)는
**`corp_events` 에 `split_factor` 를 가진 split 행이 있는 종목**의 **모든 날짜**
`adj_factor` 를 이벤트 기준으로 **다시 계산해 덮어쓴다**(1.0 도 포함).

🔑 ***지금 DB 에 있는 틀린 계수(§5-1 의 9종목, 최대 24.3배)가 나온 곳이 바로 그 경로다.***
⇒ 그 종목들에 대해 이 도구가 쓴 정확한 계수는 **다음 EOD 에 같은 틀린 값으로 되돌아간다.**
그 종목에서 **지속되는 것은 OHLC 보정뿐**이다(가격은 위 1·2번 창 밖이면 안 건드려진다).

- **도구 쪽 조치(구현 완료 · 읽기 전용)**: CLI 가 종목마다 `corp_events` 를 SELECT 해
  해당하면 「이 종목의 `adj_factor` 는 다음 EOD 에 덮어써진다」고 **경고를 인쇄**하고,
  실행 요약에 그 종목 수를 남긴다. **막지는 않는다** — OHLC 보정만으로도 불가능봉은 사라진다.
- **지속되는 해법**: 🔴 ***틀린 `corp_events` 행 자체를 고치는 것***(`meta.split_factor`·
  `meta.direction`·권리락일). 그래야 `update_adj_factors` 가 «정확한 값을» 재생산한다.
  **이건 이 문서의 범위 밖이고 별도 승인 사항이다** — 라이브 수집 산출물을 고치는 일이라
  §6 검증 완료 후 사장님 승인으로 진행한다. (계수를 매번 다시 발라 버티는 것은
  「매일 지는 싸움」이므로 대안이 아니다.)
- ⚠️ 우회로 없음 확인: `update_adj_factors` 를 **끄거나 조건부로 만드는 것은 라이브 코드
  변경**이라 이 브랜치의 「라이브 0줄」 성질을 깬다. 그래서 **경고만** 한다.
