### 7-3. 🔴 어제 보고서의 표현을 정정합니다

어제 보고서 §9-4 는 **「덮어쓰기 차단 건수는 `logger.debug` 라 INFO 로그에 안 찍힌다」**고 썼습니다. **오늘 코드를 읽어보니 그보다 나쁩니다.**

- `db/repositories/price.py:128-130` 의 `logger.debug` 는 **차단 수를 「직접」 찍지 않습니다** — 찍는 값은 `len(past_rows)`(제시행)와 `len(today_rows)` 뿐입니다.
- ⇒ 🔑 **차단 건수를 「직접」 찍는 문장은 애초에 존재하지 않습니다.** 어제 보고서의 「debug 라 안 남는다」는 그 debug 가 차단 수를 찍는다는 뜻으로 읽히므로 정확하지 않습니다.
- ⚠️ **다만 「로그로는 불가능하다」고까지 말하면 과장입니다.** DEBUG 를 켜면 종목마다 `len(past_rows)`(제시행)가 찍히고, INFO 613행이 `n_filled`(실제 INSERT)를 찍으므로 **「제시행 − n_filled」 뺄셈으로 종목별 차단 수를 로그만으로 유도할 수 있습니다** — 오늘 7-2 가 한 7,373 − 77 과 같은 계산입니다(오늘은 제시행을 debug 가 아니라 「수집 완료 102개」에서 얻었을 뿐입니다).
- 정확한 진술은 **「지금의 INFO 로그만으로는 차단 축을 셀 수 없다. DEBUG 를 켜면 뺄셈으로 유도할 수 있고, 직접 찍게 하려면 코드 변경이 필요하다」** 입니다.
- 덧: `n_filled` 는 `cursor.rowcount` 이고 **`if n_filled:` 가드**가 있어(`price.py:131-134`) **차단만 일어난 종목(n_filled=0)에는 INFO 줄이 아예 안 나옵니다.** 오늘 73종목 중 72종목이 그 경우입니다.

**저녁 `updated_at` 차분도 판별 도구가 못 됩니다 — 가정이 아니라 실측입니다:**

- `SELECT count(*) FROM daily_prices WHERE updated_at >= '2026-09-09 00:00' AND updated_at < '2026-09-09 15:00'` → **0행**
- 15:45 에 3,051,916행 + 15:46 에 142,923행 = **3,194,839행 = 표의 100%** 가 저녁에 재스탬프됨(`SELECT count(*) FROM daily_prices` = 3,194,839)
- 원인: `collectors/daily_derived.py:69` 가 **표 전체**의 returns/volatility 를 재계산합니다.
- `created_at` 도 못 씁니다 — INSERT 든 UPSERT 든 SET 목록에 없어 보존됩니다(`price.py:19-33`).

### 7-4. ⚠️ 그래도 남은 것 — 「값이 실제로 되돌았을까」

오늘 W1 대상 73종목의 과거창에서 `adj_factor ≠ 1` 인 종목은 5개(054940·053950·024850·001510·003350)뿐인데, **그 행들의 `close` 는 여전히 원주가**입니다 — 054940 은 08-11 `760`(adj 0.2) → 08-12 `3,815`(adj 1) 로 불연속, 003350 은 04-17 `48,200`(adj 5) → 04-20 `9,400`(adj 1) 로 **바로 그 −80.5% 불가능봉**입니다.

⇒ **오늘 W1 집합에는 「값 보정이 적용된 과거행」이 하나도 없습니다.** 「보정값이 살아남았다」는 **직접 증거는 오늘 확보 불가**이며 **값 수준 판정은 미해소**입니다(부록 B 15번).
